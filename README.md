轻量级告警研判引擎 (Alert Judge Engine) · version 0.4.0



轻量级 · 可配置 · 一线友好



📌 三分钟速览

- **它是什么**：一个能独立运行的小服务（采集 + 接口两个进程、一个 SQLite、一个 Web 界面），夹在 WAF 与分析师之间，扮演「告警进入研判前的经济过滤器」。它不是谁家的插件，是独立应用。
- **解决什么**：告警洪水下的成本不对等——攻击者花约 1 元制造上千条告警，防御方若全量研判要花上百元。它用近乎零成本的规则匹配，把低价值告警在进入人力 / 算力之前沉下去，让攻防成本杠杆反转。
- **我在哪里做了取舍**：
  1. **只做线性模型**：`优先级 = 单次漏洞损失 × 目标权重`（前者查表得「元」，后者仅表系统重要性 0.5~3）；成本不以除数出现，而是作为**红线**——低于红线视为「看了就亏」，告警仍展示、仅标绿。刻意不上非线性公式。
  2. **沉底放读取层，不放入库层**：告警全量入库、读取时过滤；宁可多存，也不丢可追溯性。
  3. **权重不溯以往**：分数在入库时算定，改配置不回写历史——错误同样留痕，不被粉饰。
  4. **边界留给实施方**：攻击类型枚举统一、损失表审计、数据接入等，明确不在 MVP 内。
  5. **研判定性只给三个动作**：忽略 / 排查 / 封堵。**只有「忽略」需要理由**——三个动作里只有它能凭空让告警消失；排查与封堵的下游痕迹（拉人、沟通、截图）在系统外，系统只负责登记动作，不再重复索要说明。

一句话：**不是追求最高精度，而是追求刚好够用的安全。**

这是一个专为安全运维一线人员设计的告警处理工具。它不提供炫酷的大屏特效，不堆砌复杂的功能模块，而是专注于告警过载、误报干扰和处置效率低下这三个核心问题。



它的目标是：帮助一线人员从海量告警中快速筛选出真正需要关注的内容，并通过可配置的评分和沉底机制，将有限的人力集中在高价值告警上。



但当前仅供功能验证和技术演示。请勿将其直接部署在公网环境，务必在内部网络中使用，并根据自身业务场景进行二次开发和安全加固。



💡 核心理念：与其被海量低质量告警淹没，不如建立“研判前沉底”机制，将有限的人力与计算资源聚焦在真正具有高业务风险的攻击上。



🎯 核心功能

1\. 个人沉底规则 (Personal Sink Rules)

允许一线运维人员临时编写个人规则，将确认的误报、已知业务特征或已封堵的 IP 从研判主视图中“沉底”，24 小时后自动失效。



解决“误报刷屏”和“封堵空窗期”的难题。



规则仅对创建者个人生效，互不干扰，降低风险。



2\. 单次损失排序 (Loss-Based Prioritization)

`优先级 = 单次漏洞损失（元） × 目标权重`，而非依赖黑盒的“高/中/低”评级。



单次损失：查 `attack_loss` 表——每种「攻击类型 × 等级」直接给一个**金额**（如 `RCE/CRITICAL = 50 万`；扫描/探测类固定 0.5 元）。表是普通配置文件，可由甲方按现场校准，且**改完即时生效、无需重启**。未配置的攻击类型会出现在日报的「未分类攻击类型」清单里，提示管理员补录。



目标权重：只表达**系统重要性**，约定在 0.5 ~ 3 之间小幅摆动（核心与边缘系统的差异）。权重刻意不做大——它不应该大到能翻越攻击类型之间的量级差。



红线（看了就亏）：单位处置成本**不再作为除数**，而是变成一道**红线**（默认 30 元）。低于红线的告警**照常入库、照常展示，只把优先级标绿**——把“不研判”这个决定也留在明面上。红线同样在读取层比对，改它不改写历史分数。

**把损失与红线统一成同一个单位（元），红线才真正有作用**——这是相对早期模型（资产价值 × 无量纲系数 ÷ 成本）的关键修正：量纲不一致时，红线永远是死的。



3\. 操作审计与追溯 (Audit \& Accountability)

详细记录每一次“沉底”、“启用”、“禁用”操作，形成完整的操作审计链路。



解决权责追溯难题，明确每个告警的处置责任人。



为管理层提供透明的操作日志。



4\. 研判动作只有三个 (Three Verdicts)

一线对一条告警实际只有三个动作，界面就只给三个选项：



- **忽略** —— 非攻击 / 误报，从主视图移出。**只有它需要理由**（二级枚举：`非攻击` / `留待观察` / `其他`+说明），因为只有它能凭空让告警消失。
- **排查** —— 疑似攻陷 / 内网来源，需拉人核查。同样移出主视图并标记「排查中」；**不进规则、分数保留**，可在「🔎 排查中」视图找回，便于后续主动搜查（调日志等）。
- **封堵** —— 已提交封堵。截图与沟通在系统外，系统只登记动作。



原则：**摩擦只加在“让告警消失”的那一侧，而不是均匀加在所有动作上**；能枚举的就别让人写。四个入口（单条 / IP 批量 / 聚合 / 批量）统一走同一个框——早期「聚合 / 批量」走 `prompt`、留空还会自动填默认值，等于把留痕做成了一条可一键绕过的路。



视图：主列表提供「🌐 全部 / 🏠 内网源 / 🔎 排查中」——**“移出”不等于“消失”**，被分流的告警必须有可找回来的落点，否则它就是盲区。



🧠 设计哲学：告警研判是一场经济对抗

为什么传统的“聚合”与“AI 研判”存在盲区？

攻击成本极低：攻击者可使用不到 1 元成本的扫描脚本，瞬间产生数千条告警。



研判成本极高：无论是人工还是 AI（Token 费用），处理每条告警都有边际成本（例如约 0.1 元/条）。



成本杠杆不对等：攻击者花费 1 元，防御方可能需要支付 100 元去处理。



我的解法：“研判前沉底 (Pre-Sink)” 机制

将低成本的规则匹配（误报过滤、IP 黑名单）前置到 AI 研判或人工分析之前，把无价值告警从默认视图中隐去。



关键前提：所有告警仍**全量入库、可追溯**——过滤只发生在**读取/展示层**，绝不在入库时丢弃数据。



扬汤止沸不如釜底抽薪：让攻击者难以利用低质量告警“兑子”消耗你的防御资源。



完美是死亡到来的前兆。



🛡️ 数据诚实原则：记录结果，也记录依据

错误，哪怕是错误的决定，也应当被记录，而不是被后续操作粉饰——这是安全的底线。本系统以它为设计准绳：

- 全量入库：告警被规则过滤或沉底后，数据仍然保留，只是读取时不展示。
- 不溯以往：历史告警保留其入库当时的判定，不被后来修改的配置改写。
- 留痕变更：资产、规则、沉底等操作均记录操作人、时间与前后内容，错误操作同样入账。
- 结果 + 依据：不仅保留判定结果，也要能追溯其依据（资产审计已记录权重变更的前后值）。
- 边界：诚实记录不等于无差别地永久留存；审计含原始报文，可能涉及敏感信息，合规与最小化留存需另行权衡。
- 已知待完善：priority_score 目前只记录结果，尚未记录其所依据的配置版本。

需要区分两种“回退”：**代码被回退**（从未发布、系统内本无痕迹）不等同于**运行时历史被改写**——前者无害，后者绝不允许。



这个系统开放了大量对外提供服务的接口，封闭，全部功能自己实现是不现实的，期待各位的好意见。

🧩 留给实施方的问题（MVP 不解决）

本 MVP 只保证主链路可用、可解释：`优先级 = 单次漏洞损失(攻击类型 × 等级, 元) × 目标权重`；`red_line` 是「看了就亏」的分界——低于它仍展示，只是标绿。

以下问题**不在 MVP 范围内**，交由实施 / 对接方在编写接驳脚本与文档时，结合现场自行判断解决：

1. **攻击类型枚举不统一**
   `attack_type` 取自 WAF 的 tag（如 `attack-xss` → `XSS`），不同厂商命名不同（`SQL_INJECTION` / `sqli` / `sql-injection` 可能指同一攻击）。可配置矩阵要真正生效，需先建立「厂商 tag → 标准攻击类型」的映射表。本仓库未提供该映射。
   为便于发现缺项，**日报会列出「未分类攻击类型」**（区间内出现、但 `attack_loss` 尚未配置的类型 + 条数）；管理人员评判后补录进表即可，**无需重启**（配置热加载）。

2. **损失表变更无审计**
   `config/financial_factors.yaml` 的 `attack_loss`（单次漏洞损失表）是普通配置文件，修改它不会留下「谁在何时把某条损失从 X 改成 Y」的记录。资产权重有审计，损失表没有（参见「未来规划 · 审计模块统一化」）。
   修改后**无需重启**：配置文件被改动会自动热加载，采集侧与读取侧立即使用新值。

3. **WAF 判定的 severity 可能不可靠**
   部分 WAF 一律给出 `HIGH`，会使损失表的第二维退化。编辑损失表时请**保留每个攻击类型的 `DEFAULT` 兜底行**——漏配某项时会回落到该类型的 `DEFAULT`，而不是全局默认值。

4. **资产权重的匹配语义与覆盖范围**
   权重按「目的 IP / Host」（被攻击目标）匹配，`identifier` 支持精确 IP、CIDR 网段与域名后缀。
   内网段、供应链 / 业务域名等是否纳入权重，属资产清单的覆盖策略，由实施方按需添加资产条目。
   注意：权重作用于「被攻击目标」；若某 IP 只出现在源 IP（攻击者侧），不会获得资产权重。

5. **权重不溯以往**
   优先级分数在告警**入库时算定并存盘**；之后修改资产权重只影响此后新入库的告警，历史告警分数保持不变（符合上文的「数据诚实原则」）。

6. **数据接入**
   告警数据由外部（WAF / 采集引擎）写入，属对外接口；接入方需保证写入的表结构与本项目一致。

7. **前端资源依赖公网 CDN**
   前端经 `cdn.bootcdn.net` 引入 Bootstrap 5。**内网隔离部署时该 CDN 不可达，页面会无样式**；请把 `bootstrap.min.css` / `bootstrap.bundle.min.js` 本地化到 `static/vendor/`，并改写 `static/index.html` 中的两处引用。



📐 与《安全运营资源调度理论》的对应关系

本 MVP 的评分与沉底机制，并非临时拼凑，而是《安全运营资源调度理论》（见 `/docs/MyPaper`）中核心命题的最小工程实现。关键映射如下：

1. **最优分析率 r\* → 优先级 + 红线**
   第0卷「02-基本原则摘要」给出线性模型：`r* = 1` 若 `αA > κ`，否则 `r* = 0`。对应本实现：`αA` 即**优先级** = 单次漏洞损失 × 目标权重（`Scorer._get_loss(...) * Scorer._get_target_weight(dest_ip)`）；单位处置成本 `κ` 即**红线** `red_line`——低于红线即 `r* = 0`（看了就亏），但**告警照常展示、仅标绿**，把「不研判」这个决定也留在明面上。本引擎实现的正是该理论的**线性退化情形**——理论自身亦建议先上线性模型、待数据积累再迁移到非线性公式。

2. **优先级调度最优性定理 → 按 score 降序**
   第0卷同节指出：每步选择局部成本最小的操作，在单调性与凸性条件下等价于全局最优。对应本实现：按 `priority_score` 降序排列告警，即这套「懒人贪心」策略的直接实例化。

3. **「够用就行」→ 沉底只发生在读取层**
   以近乎零成本的规则匹配前置过滤低价值告警，对应公理三「够用就行」（每步选当前成本最小的操作）；同时全量入库、读取时过滤，数据仍可追溯，对应上文的「数据诚实原则」。

4. **刻意不进 MVP 的部分**
   上文「留给实施方的问题」，对应理论中标注为 III 级、尚未验证的扩展命题（柯克霍夫参数扰动、Stackelberg 非对称、SMPC 协同等）。不实现它们，是克制，不是遗漏。

完整推导见 `/docs/MyPaper` 第0卷（导览与基础）。



🧩 沉底治理：三类沉底与各自的对冲

「沉底」不是一个动作，而是三类动机完全不同的事。本系统用同一种机制、同一套审计承载它们，但治理逻辑不同——实施方应按现场对号入座：

> **与操作动作的对应**：治理上是三类，但一线在界面上只有**三个动作**——**封堵** 对应第 1 类，**内网源豁免规则** 对应第 2 类，**忽略 / 排查** 对应第 3 类（`排查` 不写规则，`忽略` 可选同步一条 24 小时个人临时规则）。分类是给治理看的，动作是给一线用的，**不要求一一对应**。

1\. **封堵类**（已提交封堵请求）
   目的：让已封堵的 IP 不再刷屏。
   风险：补偿控制是**外部的**（防火墙是否真的封住），系统不验证。
   对冲：飞书等既有催办闭环管「有没有封堵」；报文级放通核对属外部职责（未来整合时再谈）。

2\. **白名单 / 信任域类**（业务系统通信、上下游）
   目的：把这些来源的告警与主视图分开。
   风险：**永久 + 全局**，且是攻击者首选路径（供应链、横向移动）。
   对冲：条目必须**有归属人 + 复核周期**；以公司既定白名单为**外部锚定物**，多出的、非内网的条目不允许存在。

3\. **个人忽略类**（一线自建的短期判断）
   目的：应对误报刷屏与封堵空窗期。
   风险：零摩擦自助 → 可能累积成盲区。
   对冲：**24 小时自动过期** ＋ 审计留痕 ＋ 多人多次提出时经「规则升格」收敛为长期规则。

三类共通底线：**降摩擦 ≠ 豁免**——被沉底的告警**仍然入统计、仍然可检索**（过滤只在读取/展示层，见上文「数据诚实原则」）。

> 规则采用**不可变版本**语义：修改 = 注销旧版本 + 新建新版本；已注销版本默认隐藏、仍可查。注销/禁用一条规则，其隐去的告警会自动回到主视图。

> **内网源视图**：上表第 2 类（白名单 / 信任域）在本系统里的落地形态。用 `intent=exempt` 的全局规则（如 `src_ip` 命中 `10.0.0.0/8`）定义「内网源」分区：命中的告警**始终从主视图移出**，改由「内网源视图」承载（前端「🌐 全部 / 🏠 内网源 / 🔎 排查中」切换）。三点须知：
> - 这是**分区，不是沉底**——统计口径不分离，命中的告警仍计入 `total` / `rule_sunk`；
> - 一条告警若**同时**命中「内网源豁免」与「沉底规则」，会出现在**内网源视图**里（豁免优先）；
> - 未配置任何豁免规则时，内网源视图为空。
