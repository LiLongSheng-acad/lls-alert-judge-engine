轻量级告警研判引擎 (Alert Judge Engine) · version 0.3.0



轻量级 · 可配置 · 一线友好



📌 三分钟速览

- **它是什么**：一个能独立运行的小服务（采集 + 接口两个进程、一个 SQLite、一个 Web 界面），夹在 WAF 与分析师之间，扮演「告警进入研判前的经济过滤器」。它不是谁家的插件，是独立应用。
- **解决什么**：告警洪水下的成本不对等——攻击者花约 1 元制造上千条告警，防御方若全量研判要花上百元。它用近乎零成本的规则匹配，把低价值告警在进入人力 / 算力之前沉下去，让攻防成本杠杆反转。
- **我在哪里做了取舍**：
  1. **只做线性模型**：`优先级 = 资产权重 × 危害指数 ÷ 处置成本`，刻意不上非线性公式——那是理论中「待数据积累后再迁移」的部分。
  2. **沉底放读取层，不放入库层**：告警全量入库、读取时过滤；宁可多存，也不丢可追溯性。
  3. **权重不溯以往**：分数在入库时算定，改配置不回写历史——错误同样留痕，不被粉饰。
  4. **边界留给实施方**：攻击类型枚举统一、危害矩阵审计、数据接入等，明确不在 MVP 内。

一句话：**不是追求最高精度，而是追求刚好够用的安全。**



这是一个专为安全运维一线人员设计的告警处理工具。它不提供炫酷的大屏特效，不堆砌复杂的功能模块，而是专注于告警过载、误报干扰和处置效率低下这三个核心问题。



它的目标是：帮助一线人员从海量告警中快速筛选出真正需要关注的内容，并通过可配置的评分和沉底机制，将有限的人力集中在高价值告警上。



但当前仅供功能验证和技术演示。请勿将其直接部署在公网环境，务必在内部网络中使用，并根据自身业务场景进行二次开发和安全加固。



💡 核心理念：与其被海量低质量告警淹没，不如建立“研判前沉底”机制，将有限的人力与计算资源聚焦在真正具有高业务风险的攻击上。



🎯 核心功能

1\. 个人沉底规则 (Personal Sink Rules)

允许一线运维人员临时编写个人规则，将确认的误报、已知业务特征或已封堵的 IP 从研判主视图中“沉底”，24 小时后自动失效。



解决“误报刷屏”和“封堵空窗期”的难题。



规则仅对创建者个人生效，互不干扰，降低风险。



2\. 成本驱动排序 (Cost-Driven Prioritization)

基于 “预期损失” 与 “研判成本” 的量化模型，动态计算告警优先级，而非依赖黑盒的“高/中/低”评级。



资产价值：区分核心系统与边缘系统，赋予不同的权重。



攻击危害：根据攻击类型（如 RCE、SQLi、XSS）量化风险指数。



研判成本：将人力工时或 AI Token 费用纳入成本模型，计算投入产出比。



3\. 操作审计与追溯 (Audit \& Accountability)

详细记录每一次“沉底”、“启用”、“禁用”操作，形成完整的操作审计链路。



解决权责追溯难题，明确每个告警的处置责任人。



为管理层提供透明的操作日志。



🧠 设计哲学：告警研判是一场经济对抗

为什么传统的“聚合”与“AI 研判”存在盲区？

攻击成本极低：攻击者可使用不到 1 元成本的扫描脚本，瞬间产生数千条告警。



研判成本极高：无论是人工还是 AI（Token 费用），处理每条告警都有边际成本（例如约 0.1 元/条）。



成本杠杆不对等：攻击者花费 1 元，防御方可能需要支付 100 元去处理。



我的解法：“研判前沉底 (Pre-Sink)” 机制

将低成本的规则匹配（误报过滤、IP 黑名单）前置到 AI 研判或人工分析之前，把无价值告警从默认视图中隐去。



关键前提：所有告警仍**全量入库、可追溯**——过滤只发生在**读取/展示层**，绝不在入库时丢弃数据。



扬汤止沸不如釜底抽薪：让攻击者难以利用低质量告警“兑子”消耗你的防御资源。



完美是死亡到来的前兆。



🛡️ 数据诚实原则：记录结果，也记录依据

错误，哪怕是错误的决定，也应当被记录，而不是被后续操作粉饰——这是安全的底线。本系统以它为设计准绳：

- 全量入库：告警被规则过滤或沉底后，数据仍然保留，只是读取时不展示。
- 不溯以往：历史告警保留其入库当时的判定，不被后来修改的配置改写。
- 留痕变更：资产、规则、沉底等操作均记录操作人、时间与前后内容，错误操作同样入账。
- 结果 + 依据：不仅保留判定结果，也要能追溯其依据（资产审计已记录权重变更的前后值）。
- 边界：诚实记录不等于无差别地永久留存；审计含原始报文，可能涉及敏感信息，合规与最小化留存需另行权衡。
- 已知待完善：priority_score 目前只记录结果，尚未记录其所依据的配置版本。

需要区分两种“回退”：**代码被回退**（从未发布、系统内本无痕迹）不等同于**运行时历史被改写**——前者无害，后者绝不允许。



这个系统开放了大量对外提供服务的接口，封闭，全部功能自己实现是不现实的，期待各位的好意见。

🧩 留给实施方的问题（MVP 不解决）

本 MVP 只保证主链路可用、可解释：`优先级 = 目标资产权重 × WAF(等级, 攻击方式) 危害指数 ÷ 处置成本`。

以下问题**不在 MVP 范围内**，交由实施 / 对接方在编写接驳脚本与文档时，结合现场自行判断解决：

1. **攻击类型枚举不统一**
   `attack_type` 取自 WAF 的 tag（如 `attack-xss` → `XSS`），不同厂商命名不同（`SQL_INJECTION` / `sqli` / `sql-injection` 可能指同一攻击）。可配置矩阵要真正生效，需先建立「厂商 tag → 标准攻击类型」的映射表。本仓库未提供该映射。

2. **危害矩阵变更无审计**
   `config/financial_factors.yaml` 的 `attack_hazard` 是普通配置文件，修改它不会留下「谁在何时把某个指数从 X 改成 Y」的记录。资产权重有审计，矩阵没有（参见「未来规划 · 审计模块统一化」）。

3. **WAF 判定的 severity 可能不可靠**
   部分 WAF 一律给出 `HIGH`，会使矩阵的第二维退化。编辑矩阵时请**保留每个攻击类型的 `DEFAULT` 兜底行**——漏配某项时会回落到该类型的 `DEFAULT`，而不是全局默认值。

4. **资产权重的匹配语义与覆盖范围**
   权重按「目的 IP / Host」（被攻击目标）匹配，`identifier` 支持精确 IP、CIDR 网段与域名后缀。
   内网段、供应链 / 业务域名等是否纳入权重，属资产清单的覆盖策略，由实施方按需添加资产条目。
   注意：权重作用于「被攻击目标」；若某 IP 只出现在源 IP（攻击者侧），不会获得资产权重。

5. **权重不溯以往**
   优先级分数在告警**入库时算定并存盘**；之后修改资产权重只影响此后新入库的告警，历史告警分数保持不变（符合上文的「数据诚实原则」）。

6. **数据接入**
   告警数据由外部（WAF / 采集引擎）写入，属对外接口；接入方需保证写入的表结构与本项目一致。



📐 与《安全运营资源调度理论》的对应关系

本 MVP 的评分与沉底机制，并非临时拼凑，而是《安全运营资源调度理论》（见 `/docs/MyPaper`）中核心命题的最小工程实现。关键映射如下：

1. **最优分析率 r\* → 评分与忽略阈值**
   第0卷「02-基本原则摘要」给出线性模型：`r* = 1` 若 `αA > κ`，否则 `r* = 0`。对应本实现：潜在损失 `αA` = 资产权重 × 危害指数（`Scorer._get_asset_value(dest_ip) * _get_hazard_index(...)`），单位处置成本 `κ` = `cost_per_alert`，故 `priority_score = αA / κ`；`ignore_threshold` 即 `r* = 0` 的分界。本引擎实现的正是该理论的**线性退化情形**——理论自身亦建议先上线性模型、待数据积累再迁移到非线性公式。

2. **优先级调度最优性定理 → 按 score 降序**
   第0卷同节指出：每步选择局部成本最小的操作，在单调性与凸性条件下等价于全局最优。对应本实现：按 `priority_score` 降序排列告警，即这套「懒人贪心」策略的直接实例化。

3. **「够用就行」→ 沉底只发生在读取层**
   以近乎零成本的规则匹配前置过滤低价值告警，对应公理三「够用就行」（每步选当前成本最小的操作）；同时全量入库、读取时过滤，数据仍可追溯，对应上文的「数据诚实原则」。

4. **刻意不进 MVP 的部分**
   上文「留给实施方的问题」，对应理论中标注为 III 级、尚未验证的扩展命题（柯克霍夫参数扰动、Stackelberg 非对称、SMPC 协同等）。不实现它们，是克制，不是遗漏。

完整推导见 `/docs/MyPaper` 第0卷（导览与基础）。
